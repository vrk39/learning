Java Garbage Collection: Deep Mastery & Interview Guide

1. The "Fast Learning" Summary (TL;DR)​

  • The Generational Hypothesis: The JVM splits the heap into Young and Old generations because empirically, most objects die almost immediatelyspan_0span_0. This allows the GC to cheaply and frequently check "likely garbage" (Young Gen) while rarely checking "likely alive" objects (Old Gen)span_1span_1.
  • The Collector Trade-off: Parallel GC optimizes total throughput by accepting long Stop-The-World (STW) pausesspan_2span_2. G1 balances throughput and latency with configurable pause-time goals, while ZGC and Shenandoah nearly eliminate STW pauses in exchange for higher CPU overheadspan_3span_3.
  • G1 Full GC is a Failure Mode: Under G1 GC, a Full GC is a single-threaded, whole-heap fallback failure mode (often due to evacuation failure), not routine behaviorspan_4span_4. Regular steady-state operation consists of Young-only and Mixed GCsspan_5span_5.

2. Deep Architecture & Internal Mechanics​

Minor GC & The Card Table​

New objects are bump-allocated into the Eden space, making Java allocation extremely fastspan_6span_6. When Eden fills, a Minor GC copies live objects to an active Survivor space, discarding dead objects for free simply by not copying themspan_7span_7.

To avoid scanning the entire Old Gen for references pointing to the Young Gen during a Minor GC, the JVM uses a Card Tablespan_8span_8. A write barrier marks memory cards "dirty" whenever a write creates an Old→Young pointer, allowing the Minor GC to only scan dirty cardsspan_9span_9.

G1 GC & Concurrent Marking​

G1 divides the heap into equal-sized regions dynamically labeled as Eden, Survivor, Old, or Humongousspan_10span_10. Its concurrent marking cycle uses Snapshot-At-The-Beginning (SATB)span_11span_11. A write barrier records any reference overwritten during concurrent marking, ensuring objects reachable at the start of the cycle aren't missed if mutator threads remove their references mid-cyclespan_12span_12.

ZGC & Colored Pointers​

ZGC achieves concurrent relocation by repurposing unused upper bits of a 64-bit reference as metadata "colors" to track the reference's statespan_13span_13. When an application thread reads a reference field, a JIT-inserted load barrier checks these color bitsspan_14span_14. If the object was relocated concurrently but the pointer is stale, the load barrier transparently fixes the pointer before the thread is allowed to use itspan_15span_15.

3. Enterprise-Grade Coding Example: Escape Analysis​

Object allocation has a real cost, but the JVM can optimize this away if it can prove an object never leaves its creating methodspan_16span_16.

class Point {
    int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
}

int distanceSquaredFromOrigin(int a, int b) {
    // 1. Allocation
    Point p = new Point(a, b);      
    
    // 2. Only p.x and p.y are ever read
    return p.x * p.x + p.y * p.y;   
    
    // 3. 'p' never escapes this method's scope
}

Architectural Mechanics:

  • Scalar Replacement: Because p does not escape the method, C2 JIT compilation applies scalar replacementspan_17span_17. It treats p.x and p.y as separate local int variables that can live entirely in CPU registersspan_18span_18.
  • Zero Heap Impact: The compiled machine code never touches the heap or the allocatorspan_19span_19. There is no object header, Mark Word, or Klass Word generated, meaning the GC never sees this objectspan_20span_20.
  • Lock Elision: If there were a synchronized(p) block inside this method, the JVM would strip the locking machinery entirely, as no other thread could contend for an object that doesn't escape the local threadspan_21span_21.

5. Production Anti-Patterns​

  1. Unbounded HashMap Caching: Using a plain HashMap for an LRU cache with manual size checks is not thread-safe under concurrent access and is a classic root cause of heap leaksspan_29span_29. Instead, use a purpose-built library like Caffeine or Guava Cache with explicit maximumSize or expireAfterWrite policiesspan_30span_30.
  2. "Fixing" Metaspace Leaks by Raising the Limit: Increasing -XX:MaxMetaspaceSize does not fix classloader leaks; it only postpones the unbounded growth until the available native memory is eventually exhaustedspan_31span_31. The actual fix ensures that nothing outside a classloader's intended lifetime survives past a redeploymentspan_32span_32.
