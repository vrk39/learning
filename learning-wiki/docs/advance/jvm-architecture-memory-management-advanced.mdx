## 1. Deep Knowledge Guide

### 1.1 JVM Architecture — the Big Picture
The JVM has three major subsystems: the **class loader subsystem** (loading, linking — verify/prepare/resolve, initialization), **runtime data areas** (heap, per-thread stacks, Metaspace, PC registers, native method stacks), and the **execution engine** (interpreter, JIT compilers — C1/client and C2/server tiers, garbage collector). Understanding which memory area a given failure belongs to is the single most useful architect-level diagnostic skill: `StackOverflowError` → per-thread stack (excessive/unbounded recursion depth); `OutOfMemoryError: Java heap space` → heap exhaustion; `OutOfMemoryError: Metaspace` → too many loaded classes (often a classloader leak, e.g., repeated hot-redeploys without unloading); `OutOfMemoryError: unable to create new native thread` → OS thread limit hit, not heap-related at all.

### 1.2 Classloader Delegation Model and Hierarchy
Classloaders form a parent-delegation hierarchy: bootstrap (native, loads core `java.*` classes) → platform/extension → application (system) classloader, and each custom classloader by convention delegates to its parent **first**, only loading the class itself if the parent can't find it — this prevents core classes from being shadowed by user-supplied classes of the same name (a security/consistency guarantee) and is why `java.lang.String` can never be "overridden" by an application-provided class of the same fully-qualified name under the standard delegation model.

Application servers/frameworks needing per-module isolation (each web app in Tomcat having independent versions of the same library) break strict parent-first delegation with **child-first** classloaders, which is precisely why classloader leaks are a classic long-running-server memory issue: a child classloader (and every class it loaded) can't be garbage collected while *anything* still references one of its loaded classes — including a lingering thread, a static field held by a parent-loaded singleton, or a JDBC driver registered in `DriverManager` without deregistration on undeploy.

### 1.3 Stack vs. Heap — What Actually Lives Where
Each thread has its own stack of stack frames (one per method call), holding local variables and partial results — **primitives and object references** live directly on the stack frame; the **objects themselves** always live on the heap (shared across all threads). Escape analysis (a JIT optimization, not a language guarantee) can promote genuinely non-escaping objects to **stack allocation** (or eliminate them entirely via scalar replacement) when the JIT proves an object never leaves the method/thread — but this is an opportunistic runtime optimization, never something application code should rely on for correctness or predictable memory behavior.

### 1.4 Heap Generational Structure and Why It Exists
The heap is conventionally split into **Young Generation** (Eden + two Survivor spaces) and **Old Generation**, based on the empirically-validated **generational hypothesis**: most objects die young. Minor GCs (Young-only) run frequently and cheaply because Eden is small and mostly garbage; objects surviving several Minor GCs (tracked via an age counter in the object header) get **promoted** to Old Gen. This generational split is *the* foundational design decision behind every modern collector's efficiency (Parallel, G1, ZGC, Shenandoah all still exploit this hypothesis in some form, even ZGC/Shenandoah's more region-based models). Full detail on collector internals (Card Tables, SATB, colored pointers) belongs in a dedicated GC document — this doc focuses on the memory-area/architecture layer above the collector itself.

### 1.5 JIT Compilation Tiers and Warmup
HotSpot uses **tiered compilation**: bytecode starts interpreted, hot methods (detected via invocation/loop-back-edge counters) get compiled by **C1** (client compiler — fast compilation, lighter optimization, adds profiling instrumentation) first, and the hottest methods get recompiled by **C2** (server compiler — slower compilation, heavier optimizations like aggressive inlining, loop unrolling, escape analysis) using the profiling data C1 gathered. This is the architect-level reason JVM benchmarks must always account for **warmup** — a freshly-started JVM runs everything interpreted or C1-compiled, meaningfully slower than steady-state C2-optimized code, which is also why short-lived CLI tools/serverless cold-starts see JVM startup latency that long-running services amortize away entirely.

### 1.6 Native Memory Beyond the Heap
Heap size (`-Xmx`) is not the JVM's total memory footprint — native memory also includes: **Metaspace** (class metadata, native, auto-growing unless `-XX:MaxMetaspaceSize` is capped), **thread stacks** (`-Xss` per thread × thread count — a real cost at high thread counts), **direct/off-heap `ByteBuffer`s** (`java.nio`, used heavily by I/O-heavy libraries like Netty for zero-copy I/O, capped separately via `-XX:MaxDirectMemorySize`), **JIT-compiled code cache**, and **GC-internal bookkeeping structures**. A container OOM-killed JVM despite `-Xmx` looking safely under the container's memory limit is a very common production incident caused by under-accounting for this native overhead when sizing container memory limits.

<Flashcard question="Why does the standard parent-first classloader delegation model prevent a user-supplied java.lang.String class from ever shadowing the JDK's own String class?" answer="Each classloader delegates to its parent FIRST before attempting to load a class itself. Since the bootstrap classloader (at the top of the hierarchy) already loads java.lang.String, every child classloader's delegation search finds it there first and never reaches the point of loading a user-supplied class with that same fully-qualified name." />

<Flashcard question="Why can a child classloader (and everything it loaded) fail to be garbage collected even after its associated application is 'undeployed'?" answer="A classloader and its loaded classes can only be collected once NOTHING references any class it loaded — including a lingering non-daemon thread it started, a static field in a parent-loaded singleton holding a reference to one of its objects, or an externally-registered resource like a JDBC driver left in DriverManager without deregistration. Any single lingering reference pins the entire classloader and its class graph in memory." />

<Flashcard question="What's the generational hypothesis, and why does it justify running Minor GCs (Young-only) far more frequently and cheaply than full-heap collections?" answer="The empirically-validated hypothesis that most objects die young (are short-lived). Because Eden (where new objects are allocated) is relatively small and mostly filled with garbage at any given moment, a Minor GC only needs to scan and copy the small fraction of Young Gen objects that are still alive, making it fast and frequent compared to scanning the much larger, mostly-live Old Generation." />

<Flashcard question="Why must JVM performance benchmarks always account for 'warmup', and what's happening internally during that period?" answer="HotSpot starts execution fully interpreted, then progressively compiles hot methods first via C1 (fast compile, adds profiling instrumentation) and later via C2 (slow compile, heavy optimization using C1's gathered profile data) once a method proves hot enough. A freshly-started JVM measured before this tiered compilation completes reflects interpreted/C1 performance, not the steady-state C2-optimized performance long-running services eventually reach." />

<Flashcard question="Why can a JVM get OOM-killed by its container even when -Xmx is set safely below the container's memory limit?" answer="-Xmx only bounds the JAVA HEAP, not the JVM's total memory footprint. Native memory also includes Metaspace, per-thread stacks (-Xss × thread count), off-heap/direct ByteBuffers (capped separately via -XX:MaxDirectMemorySize), the JIT code cache, and GC bookkeeping structures — all of which count against the container's cgroup memory limit but are NOT covered by -Xmx alone." />
