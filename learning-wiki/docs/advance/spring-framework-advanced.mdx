## 1. Deep Knowledge Guide

### 1.1 The IoC Container and Bean Lifecycle
Spring's `ApplicationContext` builds a **bean definition graph** from configuration (annotations, XML, or Java `@Configuration`) *before* instantiating anything — this two-phase model (define, then instantiate/wire) is what allows Spring to detect certain configuration problems (like unsatisfiable dependencies) at startup rather than lazily at first use, and it's what powers `BeanFactoryPostProcessor` (operates on bean *definitions*, before instantiation) versus `BeanPostProcessor` (operates on bean *instances*, after instantiation) — a distinction that trips up many "intermediate" Spring developers who conflate the two extension points.

Bean lifecycle order: constructor → dependency injection (field/setter) → `@PostConstruct` → `BeanPostProcessor.postProcessAfterInitialization` (this is where AOP proxies get created, wrapping the raw bean) → bean ready for use → `@PreDestroy` on container shutdown.

### 1.2 Constructor Injection vs. Field Injection — the Architect's Default
Field injection (`@Autowired` on a field) is discouraged at architect level for concrete reasons, not just style preference: it makes the class **instantiable in an invalid state** via plain `new` (bypassing Spring), it hides mandatory dependencies (no compiler-enforced "this class requires X"), and it makes the class **untestable without reflection or a Spring context** in unit tests. Constructor injection makes dependencies explicit, enables `final` fields (immutability), fails fast at object-construction time if a dependency is missing, and works naturally with plain JUnit tests (`new MyService(mockDep)`, no Spring/Mockito-reflection tricks needed).

```java
// Preferred — dependencies are explicit, final, and testable with plain `new`
@Service
public class OrderService {
    private final PaymentClient paymentClient;
    public OrderService(PaymentClient paymentClient) { this.paymentClient = paymentClient; }
}
```

### 1.3 AOP — Proxy-Based, Not True Bytecode Weaving (by default)
Spring AOP (as opposed to full AspectJ) works via **runtime proxies**: either a JDK dynamic proxy (if the bean implements at least one interface — proxies the interface) or a CGLIB subclass proxy (if not, or forced via `proxyTargetClass=true` — proxies the concrete class by subclassing it). This has a critical, frequently-missed architectural consequence: **self-invocation bypasses the proxy** — calling another `@Transactional`/`@Cacheable`-annotated method on `this` from within the same bean does **not** go through the proxy, so the aspect (transaction boundary, cache check, etc.) silently doesn't apply.

```java
@Service
public class ReportService {
    @Transactional
    public void generate() {
        this.saveInternal(); // BYPASSES the proxy — @Transactional on saveInternal() does NOT apply
    }
    @Transactional
    public void saveInternal() { ... }
}
```

The standard fixes: inject a self-reference bean (`@Lazy` self-autowiring), split the annotated method into a separate bean, or switch to full AspectJ compile-time/load-time weaving where this limitation doesn't exist (at the cost of a build-time weaving step).

### 1.4 `@Transactional` Propagation and Rollback Rules
| Propagation | Behavior when called within an existing transaction |
|---|---|
| `REQUIRED` (default) | Joins the existing transaction |
| `REQUIRES_NEW` | Suspends the current transaction, starts a brand-new independent one |
| `NESTED` | Uses a savepoint within the current transaction (rollback only to the savepoint) |
| `MANDATORY` | Throws if no transaction exists |
| `NOT_SUPPORTED` | Suspends any existing transaction, runs non-transactionally |

By default, Spring only rolls back on **unchecked** exceptions (`RuntimeException`/`Error`) — a checked exception thrown from a `@Transactional` method **commits** the transaction unless `rollbackFor` is explicitly specified. This default (inherited from EJB conventions) is a common production surprise for teams using checked exceptions for business-error signaling.

### 1.5 Bean Scopes and Their Concurrency Implications
`singleton` (default) — one instance per container, shared across all concurrent requests, so mutable instance state has the same thread-safety hazard as a shared servlet instance. `prototype` — new instance per injection point/lookup, no sharing. `request`/`session` (web-aware contexts) — scoped to the HTTP request/session, requiring a scope-aware proxy (`proxyMode=ScopedProxyMode.TARGET_CLASS`) when injected into a singleton bean, since the singleton is constructed once but must transparently delegate to the *current* request's instance on each call.
