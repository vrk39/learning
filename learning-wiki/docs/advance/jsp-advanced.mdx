## 1. Deep Knowledge Guide

### 1.1 JSP Compilation Lifecycle — It's Just a Servlet
A `.jsp` file is **translated into a `.java` servlet source file** by the container (or precompiled ahead-of-time in production setups), then compiled to a `.class` and executed exactly like a hand-written servlet. Every JSP construct maps to generated Java: template text becomes `out.write("...")` calls, scriptlets (`<% ... %>`) become inlined Java statements, and expressions (`<%= ... %>`) become `out.print(...)` calls — inside the generated servlet's `_jspService()` method (the JSP analog of `service()`). This is why JSP shares all of Servlets' threading model implications: one compiled servlet instance handles concurrent requests, so any state stored outside method-local variables (e.g., in a scriptlet-declared instance-level `<%! %>` declaration) is shared, concurrently-mutable state across requests — the exact same hazard as a raw servlet instance field.

### 1.2 The Four JSP Scopes and Their Backing Storage
| Scope | Backing object | Lifetime |
|---|---|---|
| `page` | Local to the generated servlet method | Single request-response cycle, this JSP page only (not forwarded/included pages) |
| `request` | `HttpServletRequest` attribute | Single request, survives forward()/include() to other resources |
| `session` | `HttpSession` attribute | Across multiple requests from the same client, until timeout/invalidate |
| `application` | `ServletContext` attribute | Entire application lifetime, shared across ALL clients/sessions — same concurrency hazard as servlet instance fields |

`application` scope is architecturally the most dangerous for mutable state — it's genuinely global, shared JVM-wide state across every concurrent user, requiring the same synchronization discipline as any other shared-mutable-state design.

### 1.3 Why Scriptlets Are Considered an Anti-Pattern (Architect Reasoning, Not Just Style)
Mixing Java logic (`<% %>`) directly into presentation markup violates separation of concerns and, critically, makes JSP pages **untestable** without a running servlet container and **unreviewable** for business logic correctness by anyone thinking in terms of "this is a template." The MVC-oriented fix — **JSTL** (JSP Standard Tag Library, `<c:forEach>`, `<c:if>`, etc.) plus **EL** (Expression Language, `${bean.property}`) — pushes all business logic to Java classes (controllers/beans) reachable only through simple attribute-access expressions in the view, restoring a real separation between "compute the data" (testable Java) and "render the data" (JSP as pure template).

```jsp
<%-- Anti-pattern: business logic in the view --%>
<% List<User> users = userDao.findActive(); %>
<% for (User u : users) { %> <%= u.getName() %> <% } %>

<%-- Preferred: controller populates request attribute; JSP only renders --%>
<c:forEach var="user" items="${activeUsers}">
    ${user.name}
</c:forEach>
```

### 1.4 Expression Language (EL) — Null-Safe Attribute Graph Navigation
`${bean.address.city}` silently resolves to an empty string (not a `NullPointerException`) if any link in the chain (`bean`, `address`) is null — EL is deliberately fail-soft for template rendering robustness, unlike direct Java property access. This is a double-edged design: it prevents a null in optional display data from crashing page rendering, but can also silently mask a genuine upstream bug (a missing attribute renders as blank with no error surfaced) — an architect-level trade-off between resilience and observability that teams need explicit logging/monitoring elsewhere to compensate for.

### 1.5 JSP vs. Modern Templating/View Layers
JSP's tight coupling to the servlet container (compiled per-container, container-specific JSP engine versions) and lack of natural fit for REST/JSON-first architectures has largely pushed new development toward Thymeleaf (natural-templating, testable outside a container), or away from server-rendered views entirely toward SPA frontends consuming REST/JSON APIs. Legacy JSP-based systems remain common in enterprise codebases, making understanding its execution model (rather than just tag syntax) genuinely relevant for architect-level maintenance/migration decisions.
