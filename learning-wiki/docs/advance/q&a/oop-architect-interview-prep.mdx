# Object-Oriented Programming: Architect & Tech-Lead Interview Prep

## Section 1: Basic & Intermediate Q&A

<Flashcard
  question="How do the rules of preconditions, postconditions, and invariants govern Liskov Substitution Principle (LSP) compliance?"
  answer="LSP requires that a subtype must preserve behavioral contracts established by its supertype without breaking client expectations. Specifically: (1) Preconditions cannot be strengthened in a subtype (a client passing valid inputs to the base class contract must not trigger unexpected exceptions in the subclass). (2) Postconditions cannot be weakened in a subtype (the subtype must guarantee at least all the post-state guarantees and side-effect boundaries of the base class). (3) Invariants of the base class must be strictly preserved across all subclass operations."
/>

<Flashcard
  question="What is the History Constraint (Constraint on State Changes) in LSP, and how do mutable subclasses violate it?"
  answer="The history constraint dictates that a subclass must not introduce state changes or mutations that were forbidden in the base class. For example, if a base class defines an immutable point or configuration object whose internal state cannot change after instantiation, a mutable subclass that exposes mutator methods violates the history constraint. Clients relying on base class immutability will encounter unexpected state corruption and concurrency bugs when polymorphic references mutate."
/>

<Flashcard
  question="Why is exposing raw mutable collection references via getters considered an architectural anti-pattern that shatters encapsulation invariants?"
  answer="Returning a direct reference to an internal mutable collection (like a `List` or `Map`) allows external client code to invoke modification methods (`add`, `remove`, `clear`) directly on the internal state, completely bypassing domain validation logic and breaking object invariants. True architectural encapsulation requires returning unmodifiable views (e.g., `Collections.unmodifiableList`), defensive clones, or exposing domain-specific command methods instead of raw data structures."
/>

<Flashcard
  question="Why are explicit type-code checks (`instanceof` or `switch` cascades on class tags) considered architectural code smells when implementing the Open/Closed Principle?"
  answer="Type-code checks tightly couple client and service modules, requiring developers to modify existing conditional blocks across the codebase every single time a new variant or subclass is introduced, directly violating the Open/Closed Principle. Refactoring to polymorphic dispatch moves variation handling into dedicated subclass or strategy implementations, ensuring that adding a new type requires zero modifications to existing client or controller logic."
/>

<Flashcard
  question="Contrast Role Interfaces with Header Interfaces in the context of Interface Segregation, and explain why Header Interfaces cause high enterprise coupling."
  answer="A Header Interface mirrors an entire class's public API, acting as a monolithic structural contract for an object. A Role Interface is a fine-grained, client-specific contract focused on a single capability or interaction boundary (e.g., `Loggable`, `Renderable`). Header interfaces force client modules to depend on methods they never use, creating ripple compilation effects and tight coupling when any part of the monolithic contract changes, whereas Role Interfaces isolate clients to their exact required behaviors."
/>

<Flashcard
  question="Why do strict OOP languages enforce invariant or contravariant parameter types during method overriding, and what architectural failure occurs if covariant parameters are permitted?"
  answer="In traditional object-oriented design theory, if a subclass widens a method parameter type (covariant parameter), it violates LSP because a client holding a superclass reference might pass an argument valid for the superclass contract but unsupported by the subclass's narrower expectations. Languages permitting covariant parameters require runtime checks, risking ClassCastException or unexpected argument type failures at execution time."
/>

<Flashcard
  question="How do multi-field state invariants complicate encapsulation, and how does a Rich Domain Model solve them compared to an Anemic Domain Model?"
  answer="Multi-field invariants occur when an object's validity depends on relational constraints across multiple properties (e.g., `effectiveTo` must always be chronologically after `effectiveFrom`). Anemic models with public setters allow clients to update fields individually, temporarily throwing the object into an illegal intermediate state. A Rich Domain Model prevents this by hiding setters and exposing high-level business methods (`reschedule(newStart, newEnd)`) that validate and update all interdependent fields atomically within a transaction boundary."
/>

<Flashcard
  question="How do Service Provider Interfaces (SPI) achieve runtime Open/Closed compliance without recompiling core application modules?"
  answer="SPI architectures define a stable interface contract within a core module. External modules or JARs implement this interface and register themselves via metadata configuration files (e.g., `META-INF/services/`). The core system dynamically discovers and loads these plugins via the `ServiceLoader` mechanism at runtime, allowing new business features to be integrated seamlessly without altering or recompiling a single line of core source code."
/>

<Flashcard
  question="How does the Adapter Design Pattern resolve interface pollution when integrating legacy third-party SDKs that violate ISP?"
  answer="When a third-party SDK exposes a monolithic 'fat' interface containing dozens of unrelated methods, client modules depending on it violate the Interface Segregation Principle. An Adapter wraps the third-party client and exposes a lean, role-specific custom interface tailored strictly to the client's architectural domain needs, translating calls and isolating the rest of the enterprise codebase from vendor interface bloat."
/>

<Flashcard
  question="What are the compile-time exception rules enforced during method overriding, and how do they preserve LSP substitutability?"
  answer="An overriding method in a subclass cannot throw broader or new checked exceptions than those declared in the parent method signature. If a subclass method threw an unhandled checked exception unknown to the base class contract, client code catching the base class exception type would fail to compile or crash at runtime when processing subtype references polymorphically, violating LSP substitutability."
/>

<Flashcard
  question="What architectural risks does Self-Encapsulation (calling internal getters/setters instead of raw fields) introduce in deep object inheritance hierarchies?"
  answer="While self-encapsulation allows subclasses to intercept field access, it introduces subtle state-modification side effects. If a parent class constructor invokes a setter method that has been overridden in a child class, the child method executes *before* the child constructor has finished running, operating on uninitialized child state and causing difficult-to-diagnose initialization bugs."
/>

<Flashcard
  question="How does the Template Method Pattern balance the Open/Closed Principle through controlled inversion of control?"
  answer="The Template Method pattern defines the immutable algorithmic skeleton in a base class (closed for modification) while exposing protected abstract or hook methods that subclasses can override (open for extension). This prevents subclasses from corrupting the core execution sequence while allowing localized, customized steps within pre-defined architectural boundaries."
/>

<Flashcard
  question="Why does overriding `equals()` in a subclass while adding new equality fields often break LSP equivalence contracts (Symmetry and Transitivity)?"
  answer="If a subclass `Point3D` overrides `equals()` to include a `z` coordinate comparison when compared to a base `Point2D` instance, symmetry is violated: `point2D.equals(point3D)` returns true (comparing only x and y), but `point3D.equals(point2D)` returns false. This violates LSP substitutability expectations in collection algorithms (like `HashSet` containment checks and sorting lookups), leading to erratic runtime behavior."
/>

<Flashcard
  question="How do Value Objects enforce structural encapsulation and eliminate side-effect bugs in distributed domain architectures?"
  answer="Value Objects have no conceptual identity and are strictly immutable. Because their internal state cannot change after creation, they can be safely shared across multiple entities, caching layers, or concurrent threads without defensive copying, eliminating accidental side-effect mutations that plague mutable entity references."
/>

<Flashcard
  question="Why is throwing `UnsupportedOperationException` in interface implementation methods a definitive indicator of an Interface Segregation Principle violation?"
  answer="When a class implements a fat interface but throws `UnsupportedOperationException` for methods it cannot support, it proves that the interface contract is bloated and violates ISP. Clients cannot safely rely on the interface polymorphism without runtime failures, indicating that the monolithic interface must be decomposed into smaller, cohesive role interfaces."
/>

<Flashcard
  question="What is the critical structural distinction between Subtyping (interface inheritance) and Subclassing (implementation inheritance)?"
  answer="Subtyping is about *interface compliance* and substitutability (guaranteeing that a type can be used anywhere its base type is expected, adhering to LSP). Subclassing is purely an implementation mechanism for *code reuse*, allowing a child class to inherit fields and methods from a parent class. Conflating the two—using inheritance solely for code sharing without behavioral compatibility—leads directly to LSP violations and fragile hierarchies."
/>

<Flashcard
  question="Why are covariant return types safe under LSP, whereas covariant parameter types are fundamentally unsafe?"
  answer="Covariant return types are safe because a client expecting a superclass instance receives a more specific subtype instance that guarantees at least all the properties of the base contract (the client gets more than it asked for). Conversely, covariant parameter types are unsafe because if a subclass narrows a parameter type, a client holding a superclass reference might pass an argument valid for the base contract but rejected or mishandled by the subclass, causing runtime failures."
/>

<Flashcard
  question="How do strict nullability contracts (e.g., `@NonNull` and `@Nullable` annotations) impact LSP compliance during method overriding?"
  answer="LSP is violated if a subclass widens a parameter's nullability (e.g., changing a parameter from `@NonNull` in the parent to accepting `null` in the child if the base contract disallows it, or vice versa, strengthening preconditions by rejecting a non-null input that the parent permitted). Subtypes must maintain or relax parameter nullability constraints and maintain or strengthen return nullability guarantees."
/>

<Flashcard
  question="Explain why strengthening preconditions in a subclass method violates LSP from a client-caller perspective."
  answer="Strengthening a precondition means the subclass requires more stringent conditions or narrower input ranges than its superclass promised to handle. Client code written against the superclass contract passes inputs that are valid according to the base contract, but the subclass rejects or fails on them, breaking the system because the client has no knowledge of the subclass's hidden additional constraints."
/>

<Flashcard
  question="Explain why weakening postconditions in a subclass method violates LSP from a client-caller perspective."
  answer="Weakening a postcondition means the subclass guarantees fewer outcomes, state updates, or side-effect boundaries than its superclass promised. Client code relying on the robust guarantees of the base class contract will experience downstream corruption or logic failures because the subtype fails to deliver the promised post-state."
/>

<Flashcard
  question="How do copy constructors and deep cloning routines protect encapsulation invariants against external manipulation?"
  answer="They prevent representation exposure by ensuring that when an object is initialized with or returns a mutable object graph, it creates and manages a completely independent memory clone. This guarantees that external actors cannot alter the internal state of the domain object post-instantiation, preserving object validity and state invariants."
/>

<Flashcard
  question="Why does returning a direct reference to a mutable internal collection from a getter violate encapsulation, and what is the robust architectural remedy?"
  answer="It violates encapsulation by giving external modules raw pointer access to internal fields, allowing them to mutate state without validation. The architectural remedy is to return an unmodifiable wrapper view (e.g., `Collections.unmodifiableList`), an immutable copy (`List.copyOf`), or a custom iterator stream that restricts direct structural modification."
/>

<Flashcard
  question="How does the Fragile Base Class Problem undermine OCP, and why does making classes or methods `final` mitigate it?"
  answer="The Fragile Base Class Problem occurs when modifications to a base class unintentionally break subclasses because subclasses depend on hidden parent implementation details and execution order. Making base classes or methods `final` explicitly closes them for subclass extension, preventing downstream code from coupling to internal implementation details and forcing adherence to composition instead."
/>

<Flashcard
  question="How does ISP apply to API gateway contracts and microservice client SDKs to prevent bloated payload dependencies?"
  answer="ISP requires that client SDKs and API gateway contracts be segregated into role-specific modules rather than exposing monolithic DTOs and service contracts. This ensures that a client needing only user billing metadata does not depend on massive payloads containing unrelated user profile, inventory, and analytics data, reducing network overhead and compile-time coupling."
/>

<Flashcard
  question="How does switching from direct method calls to an event-driven pub-sub mechanism enhance OCP compliance in enterprise workflows?"
  answer="An event-driven architecture decouples the event producer from its consumers. When a new business capability needs to be added, you introduce a new event listener subscriber rather than modifying the core processing class with conditional service calls, fully satisfying the Open/Closed Principle."
/>

<Flashcard
  question="What happens to LSP if a subclass overrides a method to throw a broader or novel checked exception type?"
  answer="It violates LSP because client code catching the specific checked exceptions declared by the base class contract will fail to compile or catch the unhandled novel exception thrown by the subtype, leading to unexpected runtime crashes or broken error-handling boundaries."
/>

<Flashcard
  question="What is behavioral encapsulation, and why does an anemic domain model destroy object-oriented encapsulation principles?"
  answer="Behavioral encapsulation means bundling state and the business logic operating on that state inside the same domain object. An anemic domain model strips objects of all business logic, turning them into mere data bags with public getters and setters while pushing all operations into external procedural service classes, destroying encapsulation and allowing invalid states."
/>

<Flashcard
  question="How do abstract classes enforce partial structural invariants while interfaces enforce pure behavioral contracts?"
  answer="Abstract classes can hold shared instance state (fields), constructors, and concrete methods, allowing them to enforce partial structural invariants and common initialization lifecycles across a hierarchy. Interfaces contain no shared instance state (only public static constants and method signatures), defining pure behavioral contracts ('can-do' capabilities) across unrelated types."
/>

<Flashcard
  question="Why is overriding a parent method with a blank or 'no-op' implementation a classic sign of an LSP violation?"
  answer="A no-op override indicates that the subclass does not actually support the capability promised by the base class contract. If a client invokes the method expecting the documented state change or side effect, the silent no-op leaves the system in an unexpected state, proving that the inheritance hierarchy is conceptually flawed."
/>

<Flashcard
  question="How can interface default methods introduce hidden state coupling and violate clean interface segregation?"
  answer="Interface default methods allow adding concrete behavior to interfaces, but if developers use them to inject shared state logic or complex default behaviors, it blurs the line between interfaces and abstract classes, often forcing implementing classes into unintended behavioral dependencies and violating interface segregation."
/>

<Flashcard
  question="What is the difference between nominal subtyping (compiler-enforced type checks) and behavioral subtyping (runtime semantic guarantees)?"
  answer="Nominal subtyping is checked statically by the compiler based on explicit `extends` or `implements` declarations. Behavioral subtyping is a deeper semantic guarantee ensuring that a subtype honors all pre-conditions, post-conditions, invariants, and historical constraints of the supertype, ensuring safe substitutability beyond mere syntax."
/>

<Flashcard
  question="How does the 'Fat Client' antipattern manifest when consumer modules depend on large, unsegmented interfaces?"
  answer="Consumer modules are forced to depend on methods, data structures, and dependencies they do not care about. Any change to an unused portion of the fat interface forces recompilation and redeployment of clients, creating brittle deployment pipelines and tightly coupled enterprise architectures."
/>

<Flashcard
  question="How does replacing rigid conditional logic with a dynamically loaded strategy registry achieve complete OCP compliance?"
  answer="Instead of using sprawling `switch` or `if-else` blocks to handle algorithm variants, a strategy registry maps identifiers to interface implementations. Adding a new behavior requires only writing a new strategy class and registering it, requiring zero changes to existing execution dispatcher code."
/>

<Flashcard
  question="What are the risks of exposing internal state mutators inside a fluent builder interface before the final object is built?"
  answer="If a fluent builder exposes raw mutators or allows intermediate builder states to be shared across threads or leaked before `build()` is invoked, it can lead to race conditions, partial initialization, and bypasses of object validity checks."
/>

<Flashcard
  question="Why does a subclass implementation that shifts a synchronous blocking call to an asynchronous non-blocking future break LSP if client code expects immediate results?"
  answer="If client code relies on the synchronous contract—assuming that upon method return, the operation's side effects are fully committed—substituting it with an asynchronous implementation that returns a pending future can cause race conditions, unhandled concurrency exceptions, and broken transaction boundaries."
/>

<Flashcard
  question="How do rich domain models protect state invariants during bulk batch updates or database rehydration?"
  answer="Rich domain models utilize private or package-private constructors and static factory methods or persistence hooks that validate the entire aggregate state at once during rehydration, ensuring that objects are never instantiated in an invalid intermediate state."
/>

<Flashcard
  question="Why does extending concrete, non-abstract classes for code reuse violate OCP and introduce tight coupling?"
  answer="Extending concrete classes exposes subclasses to internal implementation details and concrete state structures of the parent. Changes to the parent class ripple directly down to subclasses, creating tight vertical coupling and making it impossible to substitute alternative implementations without breaking code."
/>

<Flashcard
  question="How does role-based interface segregation decouple security permission checks from core domain business logic?"
  answer="By defining granular role interfaces (e.g., `Auditable`, `Authorizable`), security interceptors can inspect specific interface capabilities rather than querying monolithic domain classes, keeping security enforcement concerns cleanly separated from core business domain logic."
/>

<Flashcard
  question="What is the architectural danger of forcing client code to manage locks externally versus encapsulating thread-safety invariants inside the object?"
  answer="If thread-safety locks are managed externally by clients, any client forgetting to acquire the lock introduces race conditions and data corruption. Encapsulating thread-safety invariants internally within the object ensures thread safety is guaranteed by design, shielding callers from concurrency pitfalls."
/>

<Flashcard
  question="How does the classic Circle-Ellipse problem illustrate the failure of modeling behavioral hierarchy through geometric subclassing under LSP?"
  answer="An ellipse allows its width and height to be resized independently. If a circle inherits from ellipse and overrides sizing methods to keep width and height equal (to preserve circular invariants), any client code expecting standard ellipse behavior (independently resizing width) will break when passed a circle, violating LSP."
/>

## Section 2: Type Systems, Subtyping & Generics

<Flashcard
  question="What is the foundational difference between Nominal Subtyping and Structural Subtyping?"
  answer="Nominal subtyping (used in Java, C#, C++) dictates that compatibility between types is determined strictly by explicit declarations—a class must explicitly name the interface or superclass it implements or extends. Structural subtyping (used in TypeScript, Go, and OCaml) dictates that compatibility is determined entirely by an object's shape or structure (its set of methods and properties), regardless of explicit declarations. If an object has all the required members, it is accepted as a subtype."
/>

<Flashcard
  question="How does Java's Type Erasure mechanism operate at compile-time and runtime?"
  answer="Type erasure is the compiler process that removes all generic type parameters when converting source code into JVM bytecode. The compiler replaces unbounded type parameters with `Object` (or their upper bounds, e.g., `T extends Number` becomes `Number`), inserts explicit type casts where generic values are retrieved, and generates synthetic **bridge methods** when necessary to preserve polymorphic overriding semantics. At runtime, generic type information is completely absent from the class metadata, rendering parameters non-reifiable."
/>

<Flashcard
  question="Why are Java Generics invariant, and how does this invariant design prevent heap pollution?"
  answer="Java generics are invariant—meaning `List<String>` is *not* a subtype of `List<Object>`, even though `String` is a subtype of `Object`. This invariance is mandatory to prevent heap pollution. If `List<String>` could be assigned to `List<Object>`, a client holding the `List<Object>` reference could insert an `Integer` into it, corrupting the underlying `String` collection and causing unexpected `ClassCastException` failures elsewhere."
/>

<Flashcard
  question="Explain the PECS principle (Producer Extends, Consumer Super) in generic wildcard bounds."
  answer="PECS dictates how to use wildcard bounds based on data flow: **Producer Extends** (`<? extends T>`) is used when a generic structure only *produces* data (you read from it, e.g., a data source); because you only read, covariant subtyping allows any subtype of `T`. **Consumer Super** (`<? super T>`) is used when a generic structure only *consumes* data (you write into it, e.g., a sink); because you only write, contravariant subtyping allows any supertype of `T` to accept values safely."
/>

<Flashcard
  question="What causes a 'Wildcard Capture' error in the Java compiler, and how does capture conversion work?"
  answer="A wildcard capture error occurs when the compiler cannot verify type safety because an unknown wildcard type argument (`?`) needs to be referenced explicitly in a subsequent expression. Capture conversion is the compiler's internal process of opening up a wildcard `?` and replacing it with a fresh, unique, synthetic type variable (represented in error messages as `capture#1 of ? extends T`), allowing safe internal method invocation within a restricted scope."
/>

<Flashcard
  question="Why are arrays covariant in Java while generic collections are invariant?"
  answer="Arrays are legacy constructs designed to be covariant (e.g., `String[]` is a subtype of `Object[]`) to permit generic sorting and utility algorithms written before generics existed in Java 5. However, array covariance sacrifices compile-time safety for runtime checking, throwing an `ArrayStoreException` if you attempt to store an invalid type. Generics were introduced later with strict invariance to shift these safety checks entirely to compile-time."
/>

<Flashcard
  question="How do Super Type Tokens work around Java's Type Erasure limitations at runtime?"
  answer="Because generic type arguments are erased at runtime, `List<String>.class` is illegal. Super Type Tokens work around this by subclassing an anonymous generic abstract class (e.g., `new TypeReference<List<String>>(){}`). Because the generic parameter is fixed in the subclass definition, the compiler preserves it in the subclass's class file metadata (`getGenericSuperclass()`), enabling frameworks like Jackson to reconstruct complex generic types at runtime."
/>

<Flashcard
  question="What is a Recursive Type Bound, and how is it used in enterprise modeling and collections (e.g., `Comparable<T>`)"
  answer="A recursive type bound binds a generic type parameter to itself or an expression containing itself, typically written as `<T extends Comparable<T>>`. This ensures that a class or method can enforce type-safe comparisons or operations against instances of its exact same concrete subtype, preventing accidental comparisons between unrelated types at compile-time."
/>

<Flashcard
  question="How do Intersection Types function in Java generics, and how are they expressed using ampersands (`&`)?"
  answer="An intersection type allows a generic type parameter or cast expression to satisfy multiple type bounds simultaneously, expressed using the `&` symbol (e.g., `<T extends Serializable & Cloneable>`). This guarantees that any type argument passed must implement or extend all specified types, enabling fine-grained capability checks and multi-faceted contract enforcement in generic algorithms."
/>

<Flashcard
  question="What are Bridge Methods, and why does the compiler automatically generate them during generic inheritance?"
  answer="When a generic class is specialized by a subclass (e.g., `class MyNode extends Node<String>`), type erasure renames the method parameter from `String` to `Object`. However, to preserve the exact method signature expected by polymorphic callers of `Node<T>`, the compiler generates a synthetic **bridge method** taking `Object` that internally casts and delegates to the concrete `String` method, maintaining binary compatibility and runtime dispatch."
/>

<Flashcard
  question="What is an Explicit Type Witness, and when is it required during generic method invocations?"
  answer="An explicit type witness is syntax that allows a developer to specify the generic type parameter explicitly when calling a generic method, written as `.<Type>methodName(args)`. It is required when the compiler's type inference engine cannot deduce the correct type from the method arguments alone or when disambiguating overloaded generic method signatures."
/>

<Flashcard
  question="Why are parameterized generic types considered Non-Reifiable, and what restrictions does this place on `instanceof` and array creation?"
  answer="A non-reifiable type is one whose type information is partially or fully erased at runtime. Because `List<String>` and `List<Integer>` both look identical (`List.class`) to the JVM at runtime due to type erasure, you cannot use them with `instanceof` (e.g., `obj instanceof List<String>` is illegal) nor can you instantiate generic arrays directly (`new List<String>[10]` is prohibited)."
/>

<Flashcard
  question="What is Heap Pollution in Java generics, and how do `@SafeVarargs` and varargs interact with it?"
  answer="Heap pollution occurs when a variable of a parameterized type points to an object that is not of that type, typically caused by mixing generics with raw types or varargs arrays. Because varargs parameters create an underlying array of the generic type (which is non-reifiable), the compiler emits unchecked warnings. The `@SafeVarargs` annotation asserts that the method body does not perform unsafe operations on the varargs array, suppressing the warning."
/>

<Flashcard
  question="What is the Curiously Recurring Template Pattern (CRTP), and how does it achieve static polymorphism in object-oriented design?"
  answer="CRTP is an idiom where a class `Derived` inherits from a base class templated on `Derived` itself (e.g., `class Base<T extends Base<T>>`). In languages supporting static polymorphism or mixins, this allows the base class to return or manipulate instances of the exact derived type without requiring runtime downcasting, enabling fluent builders and static method inheritance."
/>

<Flashcard
  question="How do multiple bounds differ from wildcard bounds in generic class and method declarations?"
  answer="Multiple bounds (e.g., `<T extends A & B>`) are declared on type parameters to restrict the allowable concrete types a caller can supply, requiring all specified interfaces/classes to be implemented. Wildcard bounds (`<? extends A>` or `<? super A>`), by contrast, are used on instantiation sites or method parameters to express covariance or contravariance over already-bounded generic structures."
/>

## Section 3: Java-Specific OOP & JVM Internals 

<Flashcard
  question="What is the exact internal memory layout of an object instance in the HotSpot JVM?"
  answer="In the HotSpot JVM, a standard object instance layout consists of three primary components: (1) **The Mark Word**: A 64-bit (on 64-bit architectures) header containing runtime metadata such as the object's identity hash code, generational GC aging bits, and locking state flags (e.g., lightweight, heavyweight, or unlocked). (2) **The Klass Word**: A pointer pointing directly to the class metadata (the Klass structure) residing in Metaspace. (3) **Instance Data**: The raw fields defined by the class and its inheritance hierarchy, packed according to JVM field-alignment rules."
/>

<Flashcard
  question="How do Compressed OOPs (Ordinary Object Pointers) scale heap addressing up to 32GB on 64-bit architectures?"
  answer="On 64-bit architectures, pointers consume 8 bytes, which increases memory footprint and reduces CPU cache density due to pointer chasing. Compressed OOPs leverage the JVM's mandatory 8-byte object alignment rule. Because all object addresses are multiples of 8, their lowest 3 bits are always zero. The JVM zeroes out these redundant bits and shifts the memory address right by 3 bits at the hardware level, allowing 64-bit pointers to be stored as 32-bit values. This effectively doubles cache line capacity and allows compressed references to address up to 32GB of heap space."
/>

<Flashcard
  question="What is Object Alignment and Padding, and why does the JVM enforce an 8-byte boundary?"
  answer="Object alignment is the architectural rule that the total size of any object instance in memory must be a strict multiple of a specific byte boundary (typically 8 bytes in HotSpot). If the sum of an object's Mark Word, Klass Word, and instance fields does not align to an 8-byte boundary, the JVM appends **padding bytes** at the end. This is enforced because modern CPU architectures fetch memory in cache lines aligned to word boundaries; misaligned memory accesses cause hardware penalties or require multiple CPU cycles to read unaligned words."
/>

<Flashcard
  question="What is the difference between `invokevirtual`, `invokespecial`, and `invokestatic` bytecode instructions?"
  answer="`invokevirtual` is used for standard instance method dispatch where the target method is resolved dynamically at runtime based on the actual receiver object's runtime type (dynamic polymorphism using vtables). `invokespecial` is used for methods that require static, non-polymorphic binding: constructors (`<init>`), private methods, and `super` keyword calls. `invokestatic` binds directly to static class methods without requiring or receiving a `this` pointer reference."
/>

<Flashcard
  question="How does `invokeinterface` dispatch differ from `invokevirtual` in JVM bytecode execution?"
  answer="`invokevirtual` resolves methods through a class vtable, where every method is assigned a fixed, pre-calculated index, enabling constant-time $O(1)$ dispatch. Because a single class can implement multiple independent interfaces, interface method positions cannot have a single fixed global vtable index across unrelated types. Traditionally, `invokeinterface` required a linear scan through an **itable** (interface method table). Modern JVMs optimize this using polymorphic inline caches and interface dispatch stubs to approach vtable execution speeds."
/>

<Flashcard
  question="How does `invokedynamic` (indy) break rigid static bytecode binding, and what is its role in lambdas?"
  answer="Introduced in Java 7, `invokedynamic` decouples the bytecode instruction from a direct method reference. Instead, the instruction relies on a **bootstrap method** executed once at runtime to bind a `MethodHandle`. This architecture allows the JVM to execute dynamic language runtimes efficiently. For Java lambdas, `invokedynamic` invokes `LambdaMetafactory.metafactory()`, which dynamically generates the implementing class instance on the fly without upfront class-loading overhead."
/>

<Flashcard
  question="What are the exact resolution rules enforced by the JVM when a diamond inheritance collision occurs with Default Interface Methods?"
  answer="When a class inherits two conflicting default methods with the exact same signature from multiple implemented interfaces (the interface diamond problem), the JVM does not resolve it automatically; it throws a compile-time or `IncompatibleClassChangeError` runtime error unless explicitly resolved. The rules are: (1) **Classes win over interfaces**: If a superclass defines a concrete method with that signature, default methods are ignored. (2) **Sub-interfaces win**: If interface B extends interface A, B's default method takes precedence. (3) **Explicit Override**: The implementing class *must* override the method explicitly and invoke the desired parent version using `SuperInterface.super.methodName()`."
/>

<Flashcard
  question="How does Monitor Inflation work when transitioning from Lightweight Locking to Heavyweight Locking in the JVM?"
  answer="Lightweight locking uses Compare-And-Swap (CAS) instructions to store a lock record pointer in the object's Mark Word without involving operating system mutexes. When heavy thread contention occurs (multiple threads repeatedly failing their CAS spins), the lock 'inflates' into a Heavyweight Monitor (`ObjectMonitor`). The JVM replaces the Mark Word with a pointer to a native OS monitor structure, parking unwinning threads in an OS-level mutex wait queue until the owner thread releases the monitor."
/>

<Flashcard
  question="How does JIT Devirtualization and Inline Caching optimize polymorphic method dispatch at runtime?"
  answer="If profiling data reveals that a polymorphic `invokevirtual` call site receives only one concrete receiver type over time (**monomorphic call site**), the JIT compiler applies **devirtualization**, replacing the dynamic vtable lookup with a direct method call and inlining its body. For bimorphic (two types) or short-lived polymorphic call sites, the JIT uses **inline caches**—fast type-checking stubs stored directly at the call site to bypass full vtable scans."
/>

<Flashcard
  question="How does the JVM guarantee thread safety during class initialization via the `<clinit>` method?"
  answer="When a class is loaded and linked, the JVM generates a synthetic static initialization method named `<clinit>` that bundles static variable assignments and static blocks. To execute `<clinit>`, the JVM acquires an internal, global class-initialization monitor lock. This guarantees that static initialization runs exactly once per class loader in a strictly thread-safe manner, blocking any concurrent threads attempting to access or instantiate the class until initialization completes."
/>

## Section 4: Object Lifecycle, Memory & Concurrency

<Flashcard
  question="How do Escape Analysis, Scalar Replacement, and Stack Allocation work under the hood in JIT compilation to optimize heap allocations?"
  answer="Escape analysis tracks the lifetime of an object allocated within a method or thread scope. If an object's reference does not escape the method bounds (i.e., not returned, stored in a heap field, or passed to another untracked scope), the JVM applies **Stack Allocation** to place the object on the thread stack frame rather than the heap, eliminating GC pressure. If the object's fields can be completely decomposed, the JIT applies **Scalar Replacement**, tearing apart the object structure entirely and storing its primitive fields directly in CPU registers or local stack slots, bypassing object instantiation overhead."
/>

<Flashcard
  question="What are the primary Happens-Before rules established by the Java Memory Model (JMM), and why are they critical for inter-thread visibility?"
  answer="Happens-before is a partial ordering relationship between memory operations that guarantees memory visibility across threads. Key rules include: (1) **Program Order Rule**: Each action in a thread happens-before every subsequent action in that same thread. (2) **Monitor Lock Rule**: An unlock on a monitor lock happens-before every subsequent lock on *that same* monitor. (3) **Volatile Variable Rule**: A write to a volatile field happens-before every subsequent read of *that same* field. (4) **Thread Start/Join Rules**: Calling `thread.start()` or successfully joining a thread establishes happens-before boundaries. These rules prevent CPU instruction reordering and ensure cache coherency synchronization."
/>

<Flashcard
  question="What are Memory Fences (Load/Store barriers), and how do hardware architectures enforce sequential consistency for volatile variables?"
  answer="Memory fences are low-level CPU instructions emitted by the JVM (or hardware) to prevent instruction reordering and enforce memory visibility across CPU caches. Types include: `LoadLoad` (prevents reordering of loads), `StoreStore` (prevents reordering of stores), `LoadStore`, and `StoreLoad` (a full barrier). When a volatile write occurs, StoreStore and StoreLoad barriers ensure prior writes flush to main memory before subsequent reads or writes can execute, overriding CPU core optimization heuristics."
/>

<Flashcard
  question="What is False Sharing in multi-threaded CPU caches, and how does the `@Contended` annotation mitigate it?"
  answer="False sharing occurs when two independent threads modify separate variables that reside on the *exact same 64-byte CPU cache line*. Even though the variables are logically independent, the hardware cache coherency protocol invalidates the entire cache line across CPU cores whenever one core modifies its byte region, causing severe performance thrashing (cache ping-ponging). The `@Contended` annotation instructs the JVM to pad the surrounding memory layout with extra alignment bytes so that fields reside on distinct cache lines."
/>

<Flashcard
  question="Why is Shallow Immutability insufficient for complex domain models, and how do custom copy constructors enforce Deep Immutability?"
  answer="Shallow immutability guarantees that an object's immediate reference fields cannot be reassigned, but if those fields point to mutable objects (e.g., `Date` or internal collections), external actors can mutate the internal state through those references, violating encapsulation. Deep immutability requires that every object in the reachable object graph is also immutable. Custom copy constructors enforce this by recursively duplicating all mutable nested components during instantiation, ensuring absolute encapsulation integrity."
/>

<Flashcard
  question="What is a Safepoint, and how does the JVM coordinate Stop-The-World (STW) pauses for Garbage Collection?"
  answer="A safepoint is a specific point during program execution where the thread's execution state, local variables, and object references are fully known and consistent to the JVM (typically at method returns, loop back-edges, or allocations). When a GC pause is required, the JVM sets a global polling flag. Threads poll this flag during routine execution, reach their nearest safepoint, and suspend themselves, allowing the GC to inspect heap references safely without thread interference."
/>

<Flashcard
  question="How do Soft, Weak, and Phantom references interact with the Garbage Collector lifecycle internally?"
  answer="(1) **SoftReference**: Retained longer than strong references; cleared by the GC only when the JVM is critically low on memory, making them ideal for memory-sensitive caches. (2) **WeakReference**: Cleared eagerly during the *very next* GC cycle if no strong references remain, utilized heavily in data structures like `WeakHashMap` to prevent memory leaks from dangling keys. (3) **PhantomReference**: Enqueued into a reference queue *after* the target object's memory has already been reclaimed and finalized, used strictly in conjunction with `Cleaner` to schedule post-mortem resource deallocation safely."
/>

<Flashcard
  question="How do Lock Elision and Lock Coarsening optimize synchronization overhead during JIT compilation?"
  answer="**Lock Elision** is an optimization where the JIT compiler uses escape analysis to identify monitor locks (`synchronized`) on objects that are proven to be strictly thread-local (never escaping the current thread). The JVM completely strips out the `monitorenter` and `monitorexit` bytecode instructions, eliminating synchronization overhead entirely. **Lock Coarsening** merges multiple adjacent synchronized blocks operating on the same monitor into a single broader block, reducing repeated lock acquisition and release cycles."
/>

<Flashcard
  question="Why was the object `finalize()` method deprecated and replaced by the `Cleaner` API?"
  answer="`finalize()` execution was notoriously non-deterministic—there was no guarantee when (or even if) it would run before application shutdown. Finalizers ran on a low-priority thread, could throw uncaught exceptions that were silently swallowed, and allowed objects to 'resurrect' themselves by re-assigning `this` to a live reference, causing severe resource leaks and GC performance degradation. The `Cleaner` API leverages `PhantomReference` to execute clean-up actions asynchronously *after* object reclamation without holding strong references or allowing object resurrection."
/>

<Flashcard
  question="What are the low-level structural causes of `StackOverflowError` versus `OutOfMemoryError` in the JVM?"
  answer="A `StackOverflowError` occurs when a thread's execution call stack exceeds its fixed native stack memory limit (typically caused by infinite recursion or excessively deep method call nesting), exhausting the thread's allocated stack frames. An `OutOfMemoryError` occurs when the JVM fails to allocate memory in a managed runtime region (such as the heap, Metaspace, or direct byte buffers) because the garbage collector cannot reclaim sufficient space to satisfy a new allocation request, indicating memory exhaustion or a leak."
/>

## Section 5: Advanced Design Patterns & Architecture

<Flashcard
  question="How does Double Dispatch work mechanically in the Visitor Pattern, and why is it necessary for open-ended operations on hierarchical object structures?"
  answer="Single dispatch in object-oriented languages routes method execution based on the runtime type of a single receiver object. However, when an operation depends on the runtime types of *both* the element and the visitor, single dispatch fails. Double dispatch achieves this by executing two sequential single dispatches: (1) The client invokes `element.accept(visitor)`, dispatching on the element's concrete type. (2) Inside the `accept` implementation, the element calls back `visitor.visit(this)`, dispatching on the visitor's concrete type while passing `this` (the exact static type of the element). This decouples operations from the object structure completely, allowing new operations to be added without modifying element classes."
/>

<Flashcard
  question="What is an Aggregate Root in Domain-Driven Design (DDD), and how does it enforce transactional consistency boundaries?"
  answer="An Aggregate Root is a cluster of associated domain entities and value objects treated as a single unit for data changes. The Aggregate Root is the sole entry point; external objects are strictly forbidden from holding direct references to internal child entities. The root is responsible for enforcing all business rules, invariants, and transactional consistency boundaries across the entire internal aggregate graph during modifications, ensuring that no internal child can ever be left in an illegal state."
/>

<Flashcard
  question="What is the structural and conceptual distinction between an Entity and a Value Object in DDD?"
  answer="An **Entity** possesses a unique, persistent conceptual identity that remains constant throughout its lifecycle regardless of state changes (e.g., a `User` with an ID). Two entities are equal if their IDs match. A **Value Object** has no conceptual identity and is defined entirely by the combination of its attribute values (e.g., a `Money` amount or an `Address`). Two value objects are equal if all their fields match. Value objects must always be strictly immutable to prevent side-effect bugs when shared."
/>

<Flashcard
  question="How do Dependency Injection (DI) Containers resolve object dependency graphs, and what is the difference between Singleton and Prototype scopes?"
  answer="DI containers inspect class constructors and metadata (annotations or configurations) to build a directed acyclic graph of component dependencies, instantiating and wiring them automatically. A **Singleton scope** instructs the container to create and cache a single shared instance of the bean for the entire lifecycle of the application container. A **Prototype scope** instructs the container to instantiate a brand-new, independent object instance every single time the bean is requested."
/>

<Flashcard
  question="How does the Specification Pattern encapsulate complex, reusable business rules using functional composition?"
  answer="The Specification pattern encapsulates a business rule into a standalone predicate class or interface, allowing rules to be combined using boolean logic operations (`and`, `or`, `negate`). In modern object-oriented architectures, specifications are implemented by composing `java.util.function.Predicate` or custom interface wrappers. This prevents business logic from leaking into repositories or controllers, making complex validation and query criteria testable, reusable, and composable."
/>

<Flashcard
  question="What is Event Sourcing, and how does it fundamentally alter the persistence model compared to traditional CRUD architectures?"
  answer="In a traditional CRUD architecture, only the current state of a domain entity is persisted in database tables, overwriting previous values. In an **Event Sourcing** architecture, state is never updated directly; instead, every state-changing business action is captured as an immutable domain event (e.g., `OrderPlaced`, `PaymentReceived`) and appended to an event log. The current state of an aggregate is reconstructed dynamically at runtime by replaying the sequence of past events from the log."
/>

<Flashcard
  question="How does CQRS (Command Query Responsibility Segregation) decouple write models from read models in enterprise architectures?"
  answer="CQRS separates the data model and execution paths for write operations (**Commands**, which mutate state and enforce domain invariants via rich aggregates) from read operations (**Queries**, which fetch denormalized data optimized for UI rendering or reporting). By isolating reads from writes, systems can scale read replicas independently, optimize database query performance, and eliminate complex ORM mapping overhead."
/>

<Flashcard
  question="How does the State Design Pattern eliminate complex conditional state-machine logic compared to procedural `switch` statements?"
  answer="Procedural state machines scatter massive `switch` or `if-else` blocks across every method to check the object's current state tag before executing logic, violating OCP. The State Pattern encapsulates each state into a dedicated class implementing a common behavior interface. The context object delegates execution directly to its current state object. State transitions are handled by swapping the state reference inside the context, localizing state-specific behavior and making new states trivial to add."
/>

<Flashcard
  question="What is the difference between the Pipeline Pattern and the Chain of Responsibility Pattern?"
  answer="While both patterns pass a request along a sequence of handlers, their intent differs. **Chain of Responsibility** passes a request along a chain where *one* handler typically processes the request and terminates the chain (unless configured otherwise, like event bubbling). The **Pipeline Pattern** (commonly used in middleware architectures) passes a request through every single handler sequentially, where each handler performs preprocessing or postprocessing and explicitly invokes the next stage in the pipeline (the 'next' delegate)."
/>

<Flashcard
  question="How does the Null Object Pattern eliminate defensive `null` checks while maintaining polymorphic safety?"
  answer="The Null Object Pattern replaces `null` reference checks with an instance of a concrete subclass that implements the shared domain interface but provides neutral, do-nothing behavior. By injecting a null object instead of `null`, client code can invoke methods polymorphically without scattering defensive `if (obj != null)` conditionals throughout business logic, preventing `NullPointerException` risks and cleaning up control flow."
/>

<Flashcard
  question="What is the architectural role of an Anti-Corruption Layer (ACL) when integrating modern rich domain models with legacy systems?"
  answer="An Anti-Corruption Layer acts as a translation and isolation boundary between a modern domain model and legacy systems, third-party APIs, or external schemas. It prevents legacy architectural flaws, anemic data structures, and database-driven constraints from leaking into and corrupting the clean design of the core domain by translating incoming and outgoing data contracts."
/>

<Flashcard
  question="How do Domain Events manage decoupled side effects within an aggregate without violating transactional boundaries?"
  answer="Domain events represent something meaningful that occurred within a business transaction. Rich domain aggregates record these events internally during state mutations. Once the aggregate transaction commits successfully, the events are dispatched to local handlers or an event bus to trigger asynchronous side effects (such as sending confirmation emails or updating read models), keeping core domain logic decoupled from external infrastructure concerns."
/>

<Flashcard
  question="What is the distinction between the Factory Method pattern and the Abstract Factory pattern?"
  answer="The **Factory Method pattern** uses inheritance to delegate object creation to subclasses, providing a single virtual method to create one product type. The **Abstract Factory pattern** uses object composition, providing an interface to create entire families of related or dependent product classes without specifying their concrete implementations, ensuring consistency across product suites (e.g., UI component kits)."
/>

<Flashcard
  question="How does the Memento Pattern preserve encapsulation while capturing and restoring an object's internal state?"
  answer="The Memento pattern externalizes an object's internal state into a separate memento object so it can be restored later (e.g., for undo/redo functionality). To protect encapsulation, the Memento uses a two-interface design: a wide interface accessible exclusively to the originator object (allowing access to its private fields) and a narrow, opaque interface exposed to the caretaker (preventing external actors from reading or tampering with internal state)."
/>

<Flashcard
  question="How does the Mediator Pattern reduce spaghetti dependencies in complex user interfaces or workflow orchestrations?"
  answer="When multiple classes (colleagues) need to communicate with one another, direct point-to-point references create a tangled, high-coupling dependency web. The Mediator pattern centralizes all inter-object communications into a single mediator object. Colleagues talk exclusively to the mediator, which coordinates and routes interactions, transforming an $O(N^2)$ coupling nightmare into a clean $O(N)$ star topology."
/>
