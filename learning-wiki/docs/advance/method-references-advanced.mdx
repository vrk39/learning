## 1. Deep Knowledge Guide

### 1.1 The Four Forms and How the Compiler Resolves Them
| Form | Syntax | Equivalent Lambda |
|---|---|---|
| Static method | `ClassName::staticMethod` | `x -> ClassName.staticMethod(x)` |
| Bound instance method | `instance::method` | `x -> instance.method(x)` |
| Unbound instance method | `ClassName::instanceMethod` | `(obj, x) -> obj.instanceMethod(x)` — the receiver becomes the first lambda parameter |
| Constructor reference | `ClassName::new` | `(args) -> new ClassName(args)` |

The compiler resolves which form applies purely from the **target functional interface's SAM signature** at the call site — the same `String::length` textual reference resolves differently depending on whether it's being assigned to `Function<String,Integer>` (unbound: `s -> s.length()`) vs. some hypothetical interface expecting zero args on a captured instance. This means a method reference has **no meaning in isolation** — it's only interpretable against a target type, exactly like a lambda expression.

### 1.2 Same `invokedynamic`/`LambdaMetafactory` Machinery as Lambdas
Method references are **not** syntactic sugar that desugars into a lambda first — both lambdas and method references compile through the identical `invokedynamic` + `LambdaMetafactory` bootstrap mechanism described in the Lambda Expressions doc. The difference is purely at the `javac` front-end: a method reference doesn't need a synthetic forwarding method generated in the enclosing class the way a lambda body does, because it can directly target the existing method via a `MethodHandle` — a (usually negligible) micro-optimization avoiding one extra indirection layer.

### 1.3 Unbound Instance Method References — the Subtle Receiver-as-Parameter Rule
This is the form most likely to trip up an interview candidate:

```java
List<String> names = List.of("charlie", "alice", "bob");
names.sort(String::compareTo);        // WRONG target type — compareTo needs 2 args from Comparator<String>
names.sort(Comparator.naturalOrder()); // or:
Comparator<String> cmp = String::compareTo; // (a, b) -> a.compareTo(b) — receiver `a` becomes first param
```

`String::compareTo` as a `BiFunction<String,String,Integer>` or `Comparator<String>` means: the **first** argument supplied at call time becomes the receiver (`a.compareTo(b)`), not a pre-bound instance — this is the "unbound" form, and it's a common source of off-by-one-argument confusion versus the bound form (`someString::compareTo`, which pre-binds the receiver and only takes one further argument).

### 1.4 Constructor References and Generic Array Constructors
`ClassName::new` works for any accessible constructor whose parameter list matches the target SAM. A special case: `int[]::new` targets `IntFunction<int[]>`, letting `Stream.toArray()` produce a correctly-typed array without reflection-based generic array creation (`(T[]) new Object[n]`, which is unsound and produces `ClassCastException` risk) — `IntFunction<A[]> generator` is exactly why `toArray(IntFunction)` exists as an overload alongside plain `toArray()` (which returns `Object[]`).

```java
String[] arr = stream.toArray(String[]::new); // avoids unchecked Object[]-to-String[] cast
```
